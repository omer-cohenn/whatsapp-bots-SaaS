# Database Schema — DRAFT (Bizz_up MVP / Phase 1)

> **Status:** DRAFT for review (feeds the business + security reviewers). Produced by the DATA agent on 2026-06-16.
> **Scope:** Phase 1 MVP only — **lead collection + human handoff + AI bot builder + try-me test**, multi-tenant.
> **Explicitly OUT of scope (later phases):** booking tables (Phase 2), RAG/pgvector tables (Phase 3). Not designed here.
> **Grounding:** decisions 0001–0004, `spec/architecture.md`, the old `system-map/database-schema.md`, `security-issues.md`, and CLAUDE.md (multi-tenant `business_id` isolation + security by default).
>
> This is a clean redesign, **not** a migration of the old schema. The old schema used the owner's **email as `business_id`** (string) on the API path and a flat config file (`"client_001"`) on the webhook path — the root of the cross-tenant bugs (C2/C3/C4 + the `conversations` phone-only collision). This draft replaces that with a real `businesses` table keyed by a **UUID**.

---

## 0. Conventions (apply to every table)

- **Primary keys:** `uuid` generated by `gen_random_uuid()` (pgcrypto). Exception: `users` keeps the Google `sub` as its natural id.
- **`business_id uuid` is the tenant key** on every tenant-scoped table → `FK businesses(id) ON DELETE CASCADE`. Listed explicitly per table below.
- **Timestamps:** `timestamptz`, default `now()`. `created_at` on every table; `updated_at` where rows mutate (kept fresh by an `updated_at` trigger — *needs verification* that we add the trigger in the build phase).
- **🔒 = ENCRYPTED at rest** (application-layer authenticated encryption before insert — see §Encryption notes). All PII (phone, names, message bodies, lead answers) and the WhatsApp session key are 🔒.
- **Row-Level Security (RLS):** every tenant table gets an RLS policy `business_id = current_business_id()` as **defense-in-depth** behind the app's own `business_id` filter (Rule 2). ⚠️ The old system used the Supabase **service-role key, which bypasses RLS** (C1) — the rebuild must connect as a non-service role for tenant queries so RLS actually applies. *(needs verification during build: exact role/session-var wiring.)*
- **Indexes:** every tenant table gets an index on `business_id` (and composite indexes on the hot lookups, noted per table).
- **Naming:** `snake_case`, plural table names.

## 1. Entity overview (text diagram)

```
                         users  (Google login identity — GLOBAL, no tenant key)
                           │  id = Google "sub"
                           │
                           │  owns (created_by)
                           ▼
        ┌──────────────────────────────────────────────────────────────┐
        │                       businesses  (the tenant)                 │
        │                       id (uuid)  ← THE business_id everywhere   │
        └──────────────────────────────────────────────────────────────┘
            │ 1:N            │ 1:1            │ 1:1           │ 1:N (membership)
            ▼                ▼                ▼               ▼
   whatsapp_connections   bot_settings   (settings owner)  business_members ──► users
        │ 1:1                                                  (who can access a business)
        ▼
   whatsapp_credentials   🔒🔒  ← THE CROWN JEWEL (Baileys auth state), isolated table
            
            │ business_id
            ├───────────────┬───────────────────────────────┐
            ▼               ▼                                ▼
         leads 🔒       conversations ──1:N──► messages 🔒   bot_builder_messages
       (the answers)   (bot/human/closed)   (chat history)  (AI-assist build chat — optional)
                              │
                              └── conversations also link a lead (lead_id, nullable)
```

**Relationship summary**
- `users (1) ── (N) business_members (N) ── (1) businesses` — a user can own/access ≥1 business; the join table makes multi-owner possible later without a schema change. (MVP can run 1 owner : 1 business; the table keeps the door open.)
- `businesses (1) ── (1) whatsapp_connections` — one WhatsApp session per business (decision 0002).
- `whatsapp_connections (1) ── (1) whatsapp_credentials` — creds split into a separate max-security table.
- `businesses (1) ── (1) bot_settings` — one bot config blob per business.
- `businesses (1) ── (N) leads` — every captured lead.
- `businesses (1) ── (N) conversations (1) ── (N) messages` — handoff state + chat history (replaces the old in-memory `memory._store` / `flow_state._flows`).
- `conversations (0..1) ── (1) leads` — a conversation may produce a lead (nullable link).

### 2.3 `business_members` — who may access a business  *(tenant table)*

Join table: which users can act on which business, and in what role. **Why it exists:** the old system had no real mapping (it equated user-email = tenant), which is exactly why isolation broke. An explicit membership table is how the app answers *"does this `business_id` belong to the authenticated user?"* (Rule 2) on every request. MVP usage is simple (the owner), but this prevents a schema change when Omer adds staff/multi-owner.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` **PK** default `gen_random_uuid()` | |
| `business_id` | `uuid` → `businesses(id)` **NOT NULL** | **Tenant key.** `ON DELETE CASCADE`. |
| `user_id` | `text` → `users(id)` **NOT NULL** | The member. `ON DELETE CASCADE`. |
| `role` | `text` NOT NULL default `'owner'` | `owner` for MVP; room for `staff`/`agent` later. |
| `created_at` | `timestamptz` default `now()` | |

- **PK:** `id`.  **Unique:** `(business_id, user_id)`.
- **FKs:** `business_id → businesses(id)`, `user_id → users(id)`.
- **🔒 Encrypted:** none.
- **Tenant key:** `business_id` 🏢.
- **Indexes:** UNIQUE(`business_id, user_id`); index on `user_id` (to list a user's businesses at login).

| `status` | `text` NOT NULL default `'disconnected'` | `disconnected` / `connecting` / `qr_pending` / `connected`. (Mirrors gateway states `connecting`/`qr`/`connected`/`disconnected`; `qr_pending` = our name for `qr`.) |
| `phone_number` | `text` 🔒 | The linked WhatsApp number (from `state.creds.me.id`). **Encrypted** (it's PII — the business's number, and the join key to customer phones). |
| `qr_code` | `text` 🔒 | The current QR data-URL while `qr_pending`. **Short-lived; should be cleared once `connected`.** Encrypted because anyone who reads it during the link window can hijack the session (gateway flag #3). *(Alternative: don't persist the QR at all — stream it transiently. | `updated_at` | `timestamptz` default `now()` | |

- **PK:** `id`.  **Unique:** `business_id`, and (where set) `gateway_account_id`.
- **FKs:** `business_id → businesses(id)`.
- **🔒 Encrypted:** `phone_number`, `qr_code`.
- **Tenant key:** `business_id` 🏢.
- **Indexes:** UNIQUE(`business_id`); UNIQUE(`gateway_account_id`) (inbound routing looks up by the account that received the message).

### 2.5 `whatsapp_credentials` — the Baileys session KEY  🔒🔒  *(THE CROWN JEWEL — tenant table, maximum security)*

**The most sensitive table in the system.** Holds the Baileys **auth state** (the `creds` + signal keys that *are* the WhatsApp session). Per Omer: kept **in the schema as its own table**, **encrypted at rest**, **isolated from everything else**. This directly fixes security **M1** (today these creds sit as plaintext JSON on disk in `qr_wa_scanner/credentials/<accountId>/creds.json`). Anyone who reads this = full account takeover, so it is split off from `whatsapp_connections` to minimize who/what ever touches it.

| Column | Type | Notes |
|---|---|---|
| `business_id` | `uuid` → `businesses(id)` **PK, NOT NULL** | **Tenant key AND primary key** (exactly one cred-set per business). `ON DELETE CASCADE`. |
| `auth_state` | `bytea` 🔒🔒 | The **encrypted** Baileys auth state (the whole `state` object: `creds` + signal keys — `noiseKey`, identity keys, `me.id`). Stored as ciphertext bytes, never plaintext. This is the WhatsApp KEY Omer wants kept in the DB, encrypted. |
| `key_version` | `int` NOT NULL default `1` | Which encryption key/DEK version encrypted this row → enables key rotation without guessing (addresses the silent-decrypt-failure problem, M2). |
| `rotated_at` | `timestamptz` | Last time the row was re-encrypted under a new key. |
| `created_at` | `timestamptz` default `now()` | |
| `updated_at` | `timestamptz` default `now()` | Bumped on every Baileys `creds.update` (creds refresh often). |

- **PK:** `business_id` (1:1 with the business and with `whatsapp_connections`).
- **FKs:** `business_id → businesses(id)`. (Conceptually also 1:1 with `whatsapp_connections.business_id`.)
- **🔒 Encrypted:** `auth_state` — **always**, and with the **strongest** protection. Recommended: **envelope encryption** — a per-row/per-business data key (DEK) wrapped by a master key (KEK) held in the secret manager (decision 0004 / architecture: secrets out of `.env`), *separate* from the `ENCRYPTION_KEY` used for ordinary lead PII. The DB only ever stores ciphertext; the KEK never touches the DB. *(needs verification: KMS vs. app-held KEK — security reviewer to choose.)*
- **Tenant key:** `business_id` 🏢 (and the PK).
- **Indexes:** none needed beyond the PK.
- **Hardening notes for the security reviewer:**
  - This table should be reachable only by the **gateway/connection service role**, *not* by general dashboard/API roles (least privilege). Strict RLS + a dedicated DB role.
  - **Never** returned by any dashboard/API endpoint, never logged, never serialized into responses.
  - Decryption failure must be **loud** (fail-closed), unlike the old `decrypt()` that silently returned ciphertext (M2).
  - Keep it physically separate from `whatsapp_connections` so status reads (frequent, low-trust) never load the key (rare, high-trust).

### 2.6 `bot_settings` — the bot's brain config (TWO jsonb fields)  *(tenant table)*

Per Omer's explicit requirement, this carries **two `jsonb` fields**: `lead_steps` (the questionnaire the bot collects) and `bot_profile` (name + system prompt + tone). This is the per-business config that **moves off disk into Supabase** (old `system_prompt.json` + `menus_chat.json`; architecture upgrade 🗂️). One row per business.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` **PK** default `gen_random_uuid()` | |
| `business_id` | `uuid` → `businesses(id)` **NOT NULL UNIQUE** | **Tenant key.** UNIQUE = one config per business. `ON DELETE CASCADE`. |
| `lead_steps` | `jsonb` NOT NULL default `'[]'` | **(1)** The **questionnaire definition** — the ordered lead columns/steps the bot collects (each step: key, question text, type, validation, required, options…). This is the *shape* of a lead. |
| `bot_profile` | `jsonb` NOT NULL default `'{}'` | **(2)** `name`, `system_prompt`, `tone` / type-of-talk (e.g. "warm and pleasant"), plus language/persona. The bot's personality + instructions. |
| `handoff_keywords` | `jsonb` default `'["נציג","אדם","human","agent"]'` | Words that trigger human handoff (from old `human_escalation_keywords`). *Optional add — supports the handoff path; reviewer may fold this into `bot_profile`.* |
| `is_published` | `boolean` NOT NULL default `false` | Drives the **try-me vs live** distinction (build → test → go-live loop). `false` = still building/testing. |
| `created_at` | `timestamptz` default `now()` | |
| `updated_at` | `timestamptz` default `now()` | |

- **PK:** `id`.  **Unique:** `business_id`.
- **FKs:** `business_id → businesses(id)`.
- **🔒 Encrypted:** none — this is the business's *own* configuration (its prompt/tone/questions), not customer PII. (Reviewer note: the system prompt is business-authored content, not secret PII; left in plaintext so the engine + bot-builder can read/write it directly. Flag if Omer considers prompts confidential IP worth encrypting.)
- **Tenant key:** `business_id` 🏢.
- **Indexes:** UNIQUE(`business_id`); GIN on `lead_steps` only if we later query inside it (not needed for MVP).
- **Why two jsonb (not normalized tables):** the questionnaire and persona are read/written **as a whole** by the bot-builder and the conversation engine, change rarely, and have a flexible shape — `jsonb` matches that and keeps the MVP simple. If we later need per-step analytics we can normalize `lead_steps` into a `lead_step_definitions` table. *(noted for reviewers.)*

### 2.7 `leads` — collected customer leads (the answers)  🔒  *(tenant table)*

Every customer lead the bot captures. **PII encrypted at rest** (continues the old system's Fernet-style encryption, which the audit confirmed actually worked — M2). Scoped by `business_id`.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` **PK** default `gen_random_uuid()` | |
| `business_id` | `uuid` → `businesses(id)` **NOT NULL** | **Tenant key.** `ON DELETE CASCADE`. |
| `conversation_id` | `uuid` → `conversations(id)` | Which conversation produced it (nullable; a lead can exist without a kept conversation). `ON DELETE SET NULL`. |
| `phone` | `text` 🔒 | Customer phone. **Encrypted.** |
| `contact_name` | `text` 🔒 | Customer name if collected. **Encrypted.** |
| `answers` | `jsonb` 🔒 | The questionnaire answers (keys map to `bot_settings.lead_steps`). **Encrypted as a blob** — stored as ciphertext (e.g. `{"_": "<ciphertext>"}`), matching the old `data = {"_": "<fernet>"}` pattern so all PII inside is protected at rest. |
| `status` | `text` NOT NULL default `'new'` | `new` / `read` / `archived` — lets the dashboard mark leads handled. |
| `is_test` | `boolean` NOT NULL default `false` | `true` if produced by **try-me test mode** (so test leads don't pollute real lead lists/stats). |
| `submitted_at` | `timestamptz` default `now()` | When the lead completed. |

- **PK:** `id`.
- **FKs:** `business_id → businesses(id)`, `conversation_id → conversations(id)`.
- **🔒 Encrypted:** `phone`, `contact_name`, `answers`.
- **Tenant key:** `business_id` 🏢.
- **Indexes:** `business_id`; composite `(business_id, submitted_at DESC)` for the dashboard list; `(business_id, status)`.
- **Note vs old schema:** old `leads` stored `flow_id` (encrypted) + `phone` (encrypted) + a `data` blob. We replace `flow_id` with the richer `conversation_id` link and an explicit `is_test` flag. Phone-as-encrypted-blob behavior is preserved.

### 2.8 `conversations` — handoff state machine  *(tenant table)*

One row per (business, customer) conversation. Tracks `bot` / `human` / `closed` for **human handoff** and anchors the chat history. **Fixes the old PK bug:** the old table's PK was `phone` alone, so two businesses sharing a customer phone collided (security flag #2 / C-class). Here the PK is a UUID and uniqueness is **`(business_id, customer_phone_hash)`**.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` **PK** default `gen_random_uuid()` | |
| `business_id` | `uuid` → `businesses(id)` **NOT NULL** | **Tenant key.** `ON DELETE CASCADE`. |
| `customer_phone` | `text` 🔒 | The customer's phone. **Encrypted** (PII). |
| `customer_phone_hash` | `text` NOT NULL | **Deterministic keyed hash (HMAC)** of the phone — because you can't look up / enforce uniqueness on randomized ciphertext. Used as the lookup + uniqueness key per business. *(needs verification: HMAC key management — security reviewer.)* |
| `customer_name` | `text` 🔒 | Display name from WhatsApp (`pushName`) if present. **Encrypted.** |
| `chat_status` | `text` NOT NULL default `'bot'` | `bot` / `human` / `closed`. The handoff state. |
| `is_test` | `boolean` NOT NULL default `false` | `true` for **try-me** conversations (no real WhatsApp). |
| `current_flow_state` | `jsonb` default `'{}'` | In-progress lead-collection position (which step, partial answers). **Replaces the old volatile in-memory `flow_state._flows`** (bug: lost on restart, breaks multi-worker). Persisting it here makes flows survive restarts and work across workers. *(Reviewer note: partial answers here can contain PII mid-flow — consider encrypting this blob too, or only persisting the step index. Flagged.)* |
| `last_msg_at` | `timestamptz` | Last inbound time; drives the 60-min auto-close loop (old `close_stale_conversations`). |
| `created_at` | `timestamptz` default `now()` | |
| `updated_at` | `timestamptz` default `now()` | |

- **PK:** `id`.  **Unique:** `(business_id, customer_phone_hash)` — **this is the tenant-collision fix.**
- **FKs:** `business_id → businesses(id)`.
- **🔒 Encrypted:** `customer_phone`, `customer_name` (and consider `current_flow_state` — see note).
- **Tenant key:** `business_id` 🏢.
- **Indexes:** UNIQUE(`business_id, customer_phone_hash`) (the hot-path lookup); `(business_id, chat_status)` (dashboard "show me human-handoff chats"); `(business_id, last_msg_at)` (auto-close sweep).

### 2.9 `messages` — chat history  🔒  *(tenant table)*

The actual message log per conversation — **replaces the old in-memory `memory._store`** (volatile, capped at 10, lost on restart, broke under multi-worker). Stores both customer and bot/human turns so the dashboard can show full history and the engine can rebuild context.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` **PK** default `gen_random_uuid()` | |
| `business_id` | `uuid` → `businesses(id)` **NOT NULL** | **Tenant key** (denormalized onto messages so every query filters by it directly — Rule 2 / defense-in-depth). `ON DELETE CASCADE`. |
| `conversation_id` | `uuid` → `conversations(id)` **NOT NULL** | Parent conversation. `ON DELETE CASCADE`. |
| `role` | `text` NOT NULL | `customer` / `bot` / `human` (the owner/agent who took over). **One consistent vocabulary** — fixes the old `model`/`assistant`/`user` inconsistency (bug #4). |
| `body` | `text` 🔒 | The message text. **Encrypted** (chat content is PII / sensitive; old system logged it in plaintext — security #9). |
| `wa_message_id` | `text` | The gateway/WhatsApp message id (`messageId` from the Baileys payload) — for dedup / idempotency on inbound. |
| `direction` | `text` NOT NULL | `inbound` / `outbound`. Redundant-with-`role` but cheap and clarifies send vs receive. |
| `created_at` | `timestamptz` default `now()` | Message timestamp. |

- **PK:** `id`.
- **FKs:** `business_id → businesses(id)`, `conversation_id → conversations(id)`.
- **🔒 Encrypted:** `body`.
- **Tenant key:** `business_id` 🏢.
- **Indexes:** `(conversation_id, created_at)` (load a thread in order); `business_id`; UNIQUE(`business_id, wa_message_id`) where `wa_message_id` is set (inbound idempotency — the gateway has no retry/dedup, bug §3, so the backend must dedup).
- **Volume note:** this is the highest-row-count table. Fine for MVP; revisit partitioning/retention later.

## 4. Encryption & security notes (for the security reviewer)

- **Two separate key domains, by sensitivity:**
  1. **Crown-jewel KEK** for `whatsapp_credentials.auth_state` — strongest protection, envelope encryption, KEK in the secret manager / KMS, never in `.env`, never in the DB. Separate DB role. (Fixes M1.)
  2. **PII data key** for lead/message/phone fields (`leads`, `conversations`, `messages`, `whatsapp_connections.phone_number`/`qr_code`). Application-layer authenticated encryption (AEAD; the old system used Fernet, which is fine) keyed from the secret manager (fixes C1's "key in `.env`").
- **`key_version` columns** (on `whatsapp_credentials`; consider adding to `leads`) make **rotation** possible and let decryption **fail loudly** instead of the old silent-ciphertext-passthrough (M2).
- **Deterministic hash for lookups:** because randomized ciphertext can't be searched, `conversations.customer_phone_hash` uses a **keyed HMAC** so we can find/dedup a customer per business without storing the phone in plaintext. (Same technique available for `leads.phone` if we need lead-dedup by phone — *needs verification* if required.)
- **RLS + non-service role:** all tenant tables get RLS keyed on `business_id`; the app must connect with a role that **does not bypass RLS** (the old service-role key did — C1/C2 root cause). App-level `business_id` filtering stays mandatory regardless (Rule 2) — RLS is the second layer.
- **Tenant-collision fix is structural:** `conversations` is now keyed `(business_id, customer_phone_hash)`, and `business_id` is denormalized onto `messages` and `leads`, so there is **no** code path that keys on phone alone (the old C-class bug).
- **`is_test` everywhere it matters:** try-me traffic is tagged (`leads.is_test`, `conversations.is_test`) so test data is trivially separable and never leaks into real lead counts.
- **Inbound idempotency:** `messages.wa_message_id` (unique per business) lets the backend dedup, since the gateway has no retry/dedup/dead-letter (gateway map §6).
